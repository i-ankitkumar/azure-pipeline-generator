# azpipegen

Turn a plain-English CI/CD description into a working Azure Pipelines YAML file.

`azpipegen` reads a sentence like *"Build a Python 3.11 app, run pytest, then deploy to an
Azure Web App called demo-api on push to main"* and produces a valid, ready-to-commit
`azure-pipelines.yml` — no blank-page YAML wrangling, no digging through Microsoft's task
reference to remember whether it's `AzureWebApp@1` or `AzureRmWebAppDeployment@4` this month.

## Why

Azure Pipelines YAML is powerful but verbose, and most pipelines are built by copy-pasting
from an old project and hoping the task versions still match. `azpipegen` keeps a small
library of correct, current task definitions (build/test/lint per language, deploy per
target) and assembles them deterministically from keywords in your description — so the
output is reproducible and doesn't depend on an API being up. Pass `--enhance` and it hands
the draft to Claude to fill in exactly the gaps the deterministic pass flagged as uncertain,
the same "rules decide what, model improves the rest" split used in
[tfscan](https://github.com/i-ankitkumar/terraform-security-scanner), its sibling project.

## Install

```bash
git clone https://github.com/i-ankitkumar/azure-pipeline-generator.git
cd azure-pipeline-generator
pip install -e .
```

Requires Python 3.10+.

## Usage

```bash
azpipegen "Build a Python 3.11 app, run pytest, then deploy to an Azure Web App called demo-api on push to main"
```

```yaml
# Generated by azpipegen — https://github.com/i-ankitkumar/azure-pipeline-generator
trigger:
  branches:
    include:
    - main
stages:
- stage: Build
  displayName: Build and test
  jobs:
  - job: BuildJob
    displayName: Build
    pool:
      vmImage: ubuntu-latest
    steps:
    - task: UsePythonVersion@0
      inputs:
        versionSpec: '3.11'
      displayName: Use Python 3.11
    - script: |-
        python -m pip install --upgrade pip
        pip install -r requirements.txt
      displayName: Install dependencies
    - script: |-
        pip install pytest pytest-azurepipelines
        pytest
      displayName: Run tests (pytest)
- stage: Deploy
  displayName: Deploy
  dependsOn: Build
  condition: succeeded()
  jobs:
  - deployment: DeployJob
    displayName: Deploy
    pool:
      vmImage: ubuntu-latest
    environment: <app-name>
    strategy:
      runOnce:
        deploy:
          steps:
          - task: AzureWebApp@1
            inputs:
              azureSubscription: <service-connection-name>
              appType: webAppLinux
              appName: <app-name>
              package: $(Pipeline.Workspace)/drop/**/*.zip
            displayName: Deploy to Azure Web App '<app-name>'
```

Write straight to a file instead of stdout:

```bash
azpipegen "Node 20 project, npm, eslint, jest, deploy to AKS on push to main" -o azure-pipelines.yml
```

When something in the description isn't clear enough to act on, `azpipegen` never guesses
silently — it defaults sensibly and tells you exactly what it skipped:

```bash
$ azpipegen "Compile the thing and ship it somewhere"
! Couldn't detect a language/stack from the description; defaulted to Python.
! Mentioned a deploy step but the target wasn't recognized; no deploy stage was added.
```

Turn on AI-assisted refinement to have Claude resolve those gaps instead of just flagging them:

```bash
export ANTHROPIC_API_KEY=sk-ant-...
azpipegen "Compile the thing and ship it somewhere" --enhance
```

## Detection reference

| Input mentions... | Detected as |
|---|---|
| `python`, `pytest`, `pip`, `django`, `flask`, `fastapi`, `poetry` | language: Python |
| `node`, `npm`, `yarn`, `jest`, `react`, `typescript`, ... | language: Node.js |
| `.net`, `dotnet`, `c#`, `nunit`, `xunit` | language: .NET |
| `docker`, `dockerfile`, `container image` | language: Docker |
| `pytest` / `jest` / `mocha` / `dotnet test` / `unittest` | test framework (defaults per language if only "test" is mentioned) |
| `lint`, `eslint`, `pylint`, `flake8`, `ruff`, `black` | lint step added |
| `web app`, `app service` | deploy target: Azure Web App |
| `aks`, `kubernetes`, `k8s` | deploy target: AKS |
| `function app`, `azure function`, `serverless` | deploy target: Azure Functions |
| `on push to <branch>`, `trigger on <branch>` | trigger branches |
| `python 3.11`, `node 20`, `.net 8`, etc. | version pins |

Anything not covered here is a matter of extending `_LANGUAGE_KEYWORDS` / `_DEPLOY_KEYWORDS` in
`azpipegen/extract.py`, or just leaning on `--enhance`.

## How it works

```
"build a python app,   ──▶ extract.py (keyword rules)  ──▶ PipelineSpec
 run pytest, deploy                                          │
 to a web app..."                                             ▼
                                                       templates.py + render.py
                                                       (builds + validates YAML)
                                                              │       │
                                                    (default) │       │ --enhance
                                                              ▼       ▼
                                                       draft YAML   enhance.py → Claude
                                                              │       │
                                                              └───┬───┘
                                                                  ▼
                                                          azure-pipelines.yml
```

## Development

```bash
pip install -e ".[dev]"
pytest
```

`tests/test_extract.py` covers the keyword-detection rules across Python/Node/.NET/Docker
and each deploy target; `tests/test_render.py` round-trips the generated YAML through
`yaml.safe_load` to guarantee every output is syntactically valid, not just plausible-looking.
